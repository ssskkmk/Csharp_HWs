# Интерфейсы и инверсия зависимостей

## Задача 1.1

### 1. Почему используется List<IDamageable>

`GameSystem` нужно уметь наносить урон, а конкретный тип объекта для этого не важен. В одном `List<IDamageable>` можно хранить и `Player`, и `Trap`, поскольку оба класса реализуют нужный интерфейс. При вызове `target.TakeDamage(damage)` выполняется реализация фактического объекта: игрок теряет здоровье, а ловушка сообщает о разрушении. Это полиморфизм: одинаковый вызов через общий тип приводит к разному поведению. Если появится разрушаемая дверь с тем же интерфейсом, её можно добавить в список без изменения `ProcessDamage`. При этом готовый `List<Player>` нельзя напрямую передать вместо `List<IDamageable>`, потому что `List<T>` инвариантен: смешанный список нужно создавать с типом `List<IDamageable>`.

### 2. Соблюдает ли Trap контракт интерфейса

Формально `Trap` реализует все требуемые члены: свойство `HP` и метод `TakeDamage`, возвращающий `bool`. Сам интерфейс не описывает, что именно означает возвращаемое значение и обязан ли каждый удар уменьшать здоровье, поэтому компилятор нарушения не обнаружит. Однако из реализации `Player` можно предположить, что `true` означает «объект ещё жив», а `false` - «объект погиб». В таком случае поведение ловушки выглядит странно: метод сообщает о разрушении, но `HP` продолжает возвращать 10, а присваивание нового здоровья игнорируется. В данном `ProcessDamage` результат вызова не используется, поэтому противоречие пока не влияет на выполнение цикла, но другой код может принять неверное решение по значению `HP`. Если договориться, что `HP` отражает текущее здоровье и уничтоженный объект имеет нулевое здоровье, ловушка уже нарушает смысловой контракт; тогда нужно хранить состояние разрушения и согласовать его с `HP` и результатом метода.

### 3. Почему HealthPotion нельзя передать в ProcessDamage

`HealthPotion` реализует только `IHealable`, поэтому не является объектом типа `IDamageable`. Добавление зелья в `List<IDamageable>` вызовет ошибку компиляции из-за несовместимости типов. Передача `List<IHealable>` в `ProcessDamage` тоже не скомпилируется, поскольку метод ожидает другой тип списка. Попытка обойти проверку через приведение объекта к `IDamageable` во время выполнения закончится `InvalidCastException`, потому что нужный интерфейс не реализован. Кроме того, урон и лечение имеют разный смысл: даже отрицательное значение урона не заменяет вызов `Heal` и не гарантирует нужного поведения. Для лечения нужен отдельный метод `ProcessHeal`, работающий через контракт `IHealable`.

### 4. Что изменится после добавления IsDead

Новое свойство `bool IsDead { get; }` без реализации станет обязательной частью `IDamageable`. Поэтому его потребуется реализовать в обоих классах, которые реализуют этот интерфейс: `Player` и `Trap`. У игрока значение можно вычислять как `HP <= 0`, а ловушке понадобится настоящее состояние разрушения вместо постоянного `HP = 10`. Если свойство не добавить в эти классы, проект не соберётся: компилятор сообщит, что член интерфейса не реализован. `HealthPotion` менять не нужно, поскольку он не реализует `IDamageable`, а `GameSystem` может продолжить работу с прежними методами. Так изменение контракта затрагивает все его реализации; обязательный член нельзя просто добавить, оставив реализующие классы без изменений.

## Задача 1.2

| Утверждение | Abstract class | Interface | Объяснение |
| --- | :---: | :---: | --- |
| Может содержать поля с конкретными значениями | + | +* | Абстрактный класс может хранить состояние экземпляра. В современном интерфейсе допустимы статические поля и константы, но не поля экземпляра. |
| Может иметь полноценный конструктор | + | − | Конструктор абстрактного класса вызывается при создании наследника. У интерфейса нет конструктора экземпляра, хотя статический конструктор допустим. |

| Может содержать реализацию метода по умолчанию | + | + | В абстрактном классе можно определить обычный или виртуальный метод с телом. Начиная с C# 8, тело может иметь и метод интерфейса. |

### Система типов для Player, Enemy и NPC

```text
IDamageable
    HP
    TakeDamage(amount)

abstract Character : IDamageable
    Name, HP
    общая реализация получения урона
    |
    +-- Player : Character, IInteractable, IHealable
    +-- Enemy  : Character
    +-- NPC    : Character, IInteractable

IInteractable
    Interact()

IHealable
    Heal(amount)
```

`Player`, `Enemy` и `NPC` принадлежат к одной группе персонажей, поэтому им подходит общий абстрактный класс `Character`. В нём можно хранить имя и здоровье, задавать их в конструкторе и один раз реализовать получение урона. Абстрактность не позволит создать неопределённого персонажа без конкретного типа. Интерфейс `IInteractable` описывает отдельную способность взаимодействовать и открывать диалог: его реализуют только `Player` и `NPC`. `IHealable` реализует только `Player`, поэтому в интерфейсе врага и NPC не появится ненужный метод лечения. Общий критерий выбора такой: абстрактный класс нужен для общего состояния и реализации связанных типов, а интерфейс - для способности, которую можно независимо добавить к разным классам.

## Вопрос к задаче 2.3

Для ледяного урона нужно создать новый класс `IceDamageCalculator`, реализовать в нём `IDamageCalculator.CalculateDamage` и передать объект этого класса в конструктор `DamageSystem`. Сам `DamageSystem` уже вызывает метод интерфейса и не должен знать формулу ледяного урона. Поэтому менять его код, добавлять проверки типов или расширять `switch` не потребуется. Выбор конкретного калькулятора остаётся в месте создания объектов, например в `Main`. Это внедрение зависимости через конструктор: система обработки зависит от абстракции, а конкретный способ расчёта подставляется снаружи.
